# Guest security review

Guests may read approved business demo records only. They cannot access user administration, settings or audit logs, open creation/editing routes, or perform business mutations. The same permissions are enforced on the server, including direct HTTP requests. Hiding controls is an additional usability restriction, not the authorization boundary.

## Controls verified and changes made

- Guest permissions use an explicit list of business modules. Administration and unknown modules are denied. Administrator data helpers also reject non-admin identities before importing a live service.
- Every implemented business mutation authenticates the request and enforces module write permission before parsing mutation input or importing a business service. Tests discover all exported POST/PUT/PATCH/DELETE business handlers and exercise spoofed roles, user/creator IDs, bearer tokens, middleware headers and query parameters. Guest session creation, logout and credential-based login are separate public/session lifecycle operations, not business mutations.
- A signed guest cookie resolves only to the built-in guest identity, ID zero. Role/ID claims in a cookie payload cannot create an administrator identity. Editing the signed payload without the signing secret invalidates the cookie. Member sessions remain random, database-backed, expire after one hour and reload roles and password fingerprints from the server. Production cookies are HttpOnly, Secure, SameSite=Lax and host-only.
- The guest artifact contains only business demo data. User account records, password hashes, sessions, connection strings and audit logs are excluded. The export script now produces version 2 without an account list. Server-side data selection never uses snapshot records as authentication identities and never falls back to live records for an unknown guest ID.
- API responses, including errors, are non-cacheable and vary by cookie. Request origins, body-size bounds and shared database-backed rate limiting remain enforced. The limiter fails closed when its storage is unavailable.
- Browser response headers deny framing and MIME sniffing, restrict embedded objects/base URLs/form targets, and disable unused camera/microphone/geolocation access. This is a limited Content Security Policy, not a complete script nonce policy.
- The installed Zod dependency was updated to patched version 4.6.6 for [GHSA-mrhx-c7xc-m3w5](https://github.com/advisories/GHSA-mrhx-c7xc-m3w5). The dependency lockfile records the patched package and integrity value.
- Reviewed routes contain no credential-free administrator login, debug role override, public account-creation bypass or exposed server action. The administrator creation CLI and browser-test session helper require trusted local/database access and are not HTTP routes. Production tests check that their source files, `.env`, Prisma schema and the raw snapshot are not served by Next.js.

## Verification

Run `npm test`, `npm run typecheck`, targeted lint, and a production build. `npm run test:guest` checks read-only guest UI and denied admin/creation routes with both data connections unavailable. `npm run test:security` probes the real production HTTP server with a signed guest cookie and deliberately invalid mutation data/nonexistent IDs; it requires the configured hosted database for security rate limiting. It does not use valid business mutations. The test process uses its own local port and guest signing secret, without modifying the application's configured secret.

No test can establish that an application is impossible to compromise. This review covers the repository's implemented guest boundary and the installed dependency advisory results at review time. It does not independently audit hosting configuration, database network exposure/RLS, administrator devices, deployed secret values, TLS configuration or future code changes. Do not serve the repository root as a static website or copy private `.env`, backups or test helpers into `public/`. Deploy the updated build to activate these controls in production; removing files from the current snapshot cannot erase information already downloaded from an earlier deployment.
